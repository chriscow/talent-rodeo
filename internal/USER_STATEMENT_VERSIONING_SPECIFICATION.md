# User Statement Versioning System Specification

## Overview

The **User Statement** is a key component of the job search process. It is a
first-person narrative generated by an LLM that represents the user's job search
goals, experiences, and skills. It is used to as a "source of truth" for the job
search process.

The **User Statement Versioning System** provides comprehensive versioning,
tracking, and management of user job search statements across multiple systems.
This system enables reproducible statement generation, audit trails, and
seamless integration between transcript processing, feedback analysis, and
followup question systems and other future systems that may tweak the statement.

### Key Requirements

- **Versioned Storage**: Each statement revision stored as separate document with full history
- **System Integration**: Compatible with existing transcript, feedback, and future followup systems  
- **Reproducible Generation**: Each version stores data from the source system to regenerate the statement (prompt, data, etc.) and generates it from the previous version + new data.
- **Audit Trail**: Track what system changed statements, when, and why
- **Prompt Versioning**: Include versioned prompt files in statement generation metadata. The prompt file is stored in the assets/prompts/ directory and are versioned by file name. The prompt content does not need stored in the database, just a reference to the file name.
- **Performance**: Efficient retrieval of latest version while maintaining full history

    LLMModel              string                                // Model used for generation
    LLMTokensUsed         *int                    // Token count if available
    
    // Source Data (for regeneration)

    // Timestamps and Tracking

    CreatedBy             *string                    // User ID if manual, system if auto
    PreviousVersionID     *string                 // Reference to previous version
    
    // Change Analysis
    ChangeType            string                              // "initial", "enhancement", "correction", "feedback_driven"
    ChangeSummary         *string                 // LLM-generated summary of changes
    SignificantChange     bool                         // True if meaningful content change
}

    StepNumber            int                                 // Order of application
    TransformationType    string                      // "transcript_analysis", "feedback_integration", etc.
    InputData            map[string]any                      // Data used for this step
    OutputData           map[string]any                      // Result of transformation
    PromptUsed           string                              // Exact prompt text used
    ProcessedAt          time.Time                          
}

// Enhanced GetUserStatement function in internal/transcript/transcript_processor.go
func GetUserStatement(ctx context.Context, user *internal.User, transcript *internal.Transcript, fs *internal.FirestoreClient, logger *slog.Logger) error {
    // Check if user already has statement versions
    existing, err := user_statement.GetLatestStatement(ctx, fs, user.ID)
    if err == nil && existing != nil {
        logger.Debug("user already has statement, skipping transcript generation", "userID", user.ID, "currentVersion", existing.VersionNumber)

    // Generate initial statement using versioning system
    promptFile := "transcript.user-statement.v001.txt"
    version, err := user_statement.CreateInitialStatement(ctx, fs, user.ID, transcript, promptFile)
    if err != nil {
        return fmt.Errorf("failed to create initial statement: %w", err)
    }
    
    logger.Debug("created initial statement version", "userID", user.ID, "versionID", version.ID, "versionNumber", version.VersionNumber)
    return nil
}

### Regeneration Criteria

The regeneration process will only process users that meet **all** criteria:

1. **Have existing User.Statement != nil** (indicates completed onboarding)
2. **Have at least one completed appointment** (source of transcript)
3. **Appointment has CallID (voice) OR ChatMessages (chat)** (source data available)

Users without these criteria will be skipped:
- New users without statements (will get versioned statements on first transcript processing)
- Users who haven't completed phone calls or chat sessions
- Users with corrupted appointment data

## Error Handling and Recovery

### Data Consistency

1. **Atomic Updates**: Use Firestore transactions for version creation and User field updates to handle concurrent access
2. **Orphan Detection**: Find and clean up versions without corresponding User records
3. **Corruption Recovery**: Rebuild User.Statement field from latest version if needed
4. **Version Validation**: Ensure version number sequences are correct
5. **Concurrent Updates**: Firestore transactions prevent race conditions when multiple systems update statements simultaneously

### Failure Recovery

1. **Partial Migrations**: Resume interrupted data migrations
2. **Source Data Recovery**: Regenerate statements if source data is intact
3. **Fallback Strategies**: Use previous version if latest version is corrupted
4. **Manual Intervention**: Admin tools for fixing data inconsistencies
