# Follow-up Questions Feature Specification

## Overview

The **Follow-up Questions** feature is a sophisticated engagement system that manages personalized questions about users' job search progress. The `internal/followup` package is responsible for question aggregation, storage, and response processing, while the `internal/nudge` package handles the email delivery cadence and scheduling.

### System Distinctions: Follow-up vs. Feedback

It is crucial to distinguish between two separate systems:

-   **Follow-up System (This document):** Focuses on aggregating open-ended questions generated by LLM analysis of job descriptions (`JobMatchAnalysis.FollowUpQuestions`). It sends these questions to users via email and processes their natural language replies to gain deeper insight. This new context can then be used to re-analyze existing or future job matches for better fit assessment.

-   **Feedback System (Separate):** Refers to the UI-driven mechanism where users click "like" or "dislike" on specific job attributes (e.g., skills, qualifications). This direct feedback is used to immediately refine the user's search parameters and steering query for future job searches.

## Key Requirements

### Prerequisites
-   User must have completed their initial call (`UserStatus >= UserStatusCallCompleted`)
-   User must have new job matches processed for them by the `subscription_processor`.

### Package Responsibilities

**`internal/followup` Package**:
-   Question aggregation from job matches, triggered by an event.
-   Question storage and management in Firestore.
-   Email response processing and answer extraction via LLM.
-   Question priority ranking and deduplication.

**`internal/nudge` Package**:
-   Email delivery timing and cadence for follow-up questions.
-   User eligibility checking.
-   Email template rendering and sending.
-   Handles overall communication subscription management.

## Question Lifecycle

### 1. Question Aggregation (Event-Driven & Incremental)

The aggregation process is **event-driven** and uses an **incremental merge strategy**. This ensures timely, efficient, and cost-effective processing after new jobs are analyzed for a user, avoiding the need to re-process the entire question history on every run.

-   The new dispatcher will be triggered after `RefreshUserJobs` successfully completes processing jobs for a user.
-   It will emit an `OnUserJobsRefreshed(userID string, newJobIDs []string)` event.
-   The `internal/followup` package will register a handler for this event to begin the question aggregation process for that specific user.

**Aggregation Steps:**
1.  **Trigger**: The `OnUserJobsRefreshed` event is received for a `userID`.
2.  **Gather New Raw Questions**: The system queries `user_jobs` to collect all raw `FollowUpQuestions` from jobs that have not yet been processed (i.e., `NormalizedQuestionRefs` is empty).
3.  **Fetch Existing State**: The system queries the `user_followup_questions` collection for the `userID` to get the list of current, existing normalized questions.
4.  **LLM-Powered Incremental Merge**: Both the *new raw questions* and the *existing normalized questions* (including their Firestore IDs) are sent to the LLM. The prompt instructs the LLM to perform a stateful merge: categorize each new question under an existing normalized question or create a new one.
5.  **Process LLM Response**: The application parses the structured JSON response from the LLM.
6.  **Update Firestore**:
    -   It creates new documents in `user_followup_questions` for any newly identified normalized questions.
    -   It updates existing documents with their new `EstimatedCount` and `Priority`.
    -   It finds the original `UserJob` documents for the raw questions processed in this run and updates their `NormalizedQuestionRefs` to link them to the appropriate normalized question document.
7.  **Timestamp**: `User.FollowupQuestionsAggregatedAt` is updated.

### 2. Question Delivery (via `internal/nudge`)

-   The `internal/nudge` package queries the `user_followup_questions` collection for the highest priority, unsent questions.
-   It renders email templates with the questions and sends them according to its own scheduling and rate-limiting logic.

### 3. Response Processing (via `internal/inbox` and `internal/followup`)

1.  **Capture**: The `internal/inbox` system receives the user's email reply.
2.  **Identify**: The `internal/followup` email handler identifies the response using the tracking ID in the subject/body. It filters out auto-replies.
3.  **Extract**: The email content is passed to an LLM to extract answers into a structured format.
4.  **Store**: The extracted answers are stored in the corresponding `user_followup_questions` documents. If a question is answered again, the **most recent answer replaces the previous one**.

## LLM Interaction Details

### Question Aggregation & Normalization (Incremental Merge)

The aggregation process uses an **incremental merge strategy** to efficiently integrate new questions without costly re-aggregation of the entire history.

-   **Prompt File:** `assets/prompts/followup-question-aggregation-incremental.txt` (placeholder)
-   **Model:** DeepSeek (or other cost-effective "thinking" model)
-   **LLM Inputs:**
    1.  A list of `existing_normalized_questions` (including their unique Firestore IDs).
    2.  A list of `new_raw_questions` from the latest job batch.
-   **Prompt Goal:** Instruct the LLM to analyze the `new_raw_questions`. For each one, it must either categorize it under one of the `existing_normalized_questions` or group it into a new normalized question. The LLM should also re-evaluate priority and counts for the entire set.
-   **Expected Output (JSON):**
    ```json
    {
      "processed_questions": [
        {
          "id": "existing-firestore-doc-id-1", 
          "normalized_text": "What are the remote work arrangements and flexibility options?",
          "priority": 1,
          "type": "remote_work",
          "estimated_count": 8,
          "matched_raw_questions": [
            "How flexible are the remote work options?",
            "Can I work from home full-time?"
          ]
        },
        {
          "id": "NEW_QUESTION_1", 
          "normalized_text": "What is the team's on-call rotation policy?",
          "priority": 3,
          "type": "work_life_balance",
          "estimated_count": 2,
          "matched_raw_questions": [
            "Is there an on-call schedule?",
            "What are the on-call expectations?"
          ]
        }
      ]
    }
    ```
-   **Processing Logic:**
    1.  The application iterates through the `processed_questions` array from the LLM response.
    2.  If a question's `id` matches an existing Firestore document, it **updates** that document with the new `priority` and `estimated_count`.
    3.  If the `id` is a placeholder (e.g., starts with `NEW_`), it **creates** a new document in the `user_followup_questions` collection.
    4.  For every raw question listed in `matched_raw_questions`, the application finds its source `UserJob` document and updates the `NormalizedQuestionRefs` array to link it to the correct (new or existing) normalized question document.

### Answer Extraction from Email Responses

The LLM will parse a user's email reply to find answers to specific questions.

-   **Prompt File:** `assets/prompts/followup-answer-extraction.txt` (placeholder)
-   **Structured Output (XML):**
    ```xml
    <followup_response>
      <question_answer>
        <question_id>Q1-{firestoreDocID}</question_id>
        <question_text>What are the remote work arrangements and flexibility options?</question_text>
        <answer_found>true</answer_found>
        <answer>I'm looking for a fully remote position, but I am open to hybrid if the commute is reasonable.</answer>
      </question_answer>
      <question_answer>
        <question_id>Q2-{firestoreDocID}</question_id>
        <question_text>What is the compensation range for this role?</question_text>
        <answer_found>false</answer_found>
        <answer>N/A</answer>
      </question_answer>
      <additional_feedback>
        I'm also very interested in roles that offer a 4-day work week.
      </additional_feedback>
    </followup_response>
    ```
-   **Processing Logic:**
    -   If `answer_found` is `true`, the system updates the `Question.Answer` field.
    -   If `answer_found` is `false`, the system ignores the question.
    -   If `additional_feedback` contains text, its content will be **emailed to a support team** for manual review. It will not be stored in the database.

## Edge Case Handling

-   **User Opt-Out:** This is out of scope for this feature. Users who stop engaging with the platform will naturally stop receiving emails as no new jobs are processed for them. The system does not require a specific "unsubscribe" link for this feature alone.
-   **Zero Questions:** If a user has no new `FollowUpQuestions` after a job processing run, the aggregation event is simply not triggered or completes with no action. The user is skipped.

## Future Enhancements

### Job Re-analysis with User Responses
Once a sufficient number of questions have been answered, a process can be triggered to re-evaluate job matches.
1.  Query all `UserJob`s that have `NormalizedQuestionRefs` pointing to recently answered questions.
2.  Re-run the job match analysis LLM call, but this time include the user's answers as additional context.
3.  Update the `JobMatchAnalysis` and `Rating` on the `UserJob` to reflect the new, more accurate assessment.

### Dashboard Integration
A future phase could display the questions and answers on the user's dashboard, allowing them to answer directly via the web interface.

## Testing Strategy

**Testing Architecture Guideline**: Separate business logic from third-party API calls in function design to minimize mocking requirements. Business logic functions should accept processed data as parameters rather than making external calls directly, making them easier to test with simple inputs.

### Unit Tests
- Question generation with various user contexts
- Question deduplication logic
- Response parsing and mapping
- Timing logic for different followup days
- LLM response parsing (test with mock responses, not actual API calls)
- Email tracking ID generation and validation

### Integration Tests
- End-to-end flow from question generation to email delivery
- Response processing workflow
- Database consistency checks
- Integration with feedback system
- Email handler with mock inbox events

### Data Migration
- Add new fields to existing User documents
- Create indexes for efficient question querying
- Set up collection structure for user_followup_questions

**Example of Testable Function Design:**
```go
// Good: Business logic separated, easy to test
func ProcessQuestionResponse(questionText string, userResponse string) (*ParsedAnswer, error) {
    // Pure business logic, no external dependencies
}

func HandleEmailWithLLM(ctx context.Context, email *Email, llmClient LLMClient) error {
    // Extract text
    responseText := extractResponseText(email.Body)
    
    // Call LLM (mockable interface)
    llmResponse, err := llmClient.ParseResponse(ctx, responseText)
    if err != nil {
        return err
    }
    
    // Process response (testable business logic)
    return ProcessQuestionResponse(email.QuestionText, llmResponse.Answer)
}
```
