# Follow-up Questions Implementation Plan

This document outlines the phased implementation plan for the Follow-up Questions feature. The goal is to build the feature iteratively, with each phase delivering a testable, verifiable component that builds upon the last.

For the detailed technical blueprint of the final feature, see `FOLLOWUP_QUESTIONS_SPECIFICATION.md`.

---

### Phase 1: Foundational Data Structures & Mocked Aggregation

**Goal:** Establish the core database schema and a testable, local aggregation workflow. This phase intentionally avoids external dependencies like the LLM and event triggers to focus purely on the data transformation logic.

**Implementation Steps:**

1.  **Create Package Structure:**
    *   Create the directory `internal/followup/`.
    *   Create the initial files: `types.go`, `question_aggregator.go`, and `firestore.go`.

2.  **Define Data Structures (`types.go`):**
    *   Implement the `Question` and `EmailTracking` structs as defined in the specification.
    *   Add the `FollowupQuestionsAggregatedAt` field to the `internal.User` struct.
    *   Add the `FollowUpQuestions` and `NormalizedQuestionRefs` fields to the `internal.JobMatchAnalysis` struct.

3.  **Implement Mock Aggregation Logic (`question_aggregator.go`):**
    *   Create a primary function: `AggregateUserQuestions(ctx, userID)`.
    *   Inside this function, implement the logic to:
        *   Fetch all `UserJob` documents for the user that have `FollowUpQuestions` but haven't been processed yet.
        *   Fetch all existing `Question` documents from the `user_followup_questions` collection for that user.
        *   **Mock the LLM Call:** Create a helper function that takes the new raw questions and existing normalized questions and returns a hardcoded, structured JSON string that perfectly matches the format specified in the plan. This isolates the LLM dependency.
        *   Implement the application logic to parse this mock JSON.
        *   Use a Firestore batch write to create new `Question` documents and update existing ones based on the parsed data.

4.  **Implement Linking Logic (`firestore.go`):**
    *   Create the function `UpdateJobNormalizedQuestionRefs` to link the source `UserJob` documents to their new or existing normalized `Question` documents. This should also be part of the same batch write for atomicity.

**Acceptance Criteria:**

*   ✅ A new `internal/followup` package exists with the correct files and data structures.
*   ✅ A unit test can be executed that:
    1.  Populates a test Firestore instance with mock `UserJob`s containing raw `FollowUpQuestions`.
    2.  Populates the test Firestore with a few pre-existing `Question` documents.
    3.  Calls `AggregateUserQuestions` for the test user.
    4.  **Verifies:** The `user_followup_questions` collection now contains the correctly merged and updated `Question` documents.
    5.  **Verifies:** The original `UserJob` documents have been updated with the correct `NormalizedQuestionRefs`.

### Phase 2: Live LLM Integration & Event Trigger

**Goal:** Replace the mock aggregation with a live LLM call and trigger the entire process from a real application event, making the aggregation fully automated.

**Implementation Steps:**

1.  **Create Event Dispatcher:**
    *   In the `internal/subscription` package, create a new event dispatch system (e.g., `user_job_event_dispatch.go`) modeled after `job_event_dispatch.go`.
    *   Define a new interface, e.g., `UserJobEventHandler`, with a method like `OnUserJobsRefreshed(ctx, userID string, newJobCount int)`.
    *   Modify the `RefreshUserJobs` function in `user_job_processor.go` to call this dispatcher's `OnUserJobsRefreshed` method after it has finished processing jobs for a user.

2.  **Integrate Live LLM:**
    *   Create the placeholder prompt file: `assets/prompts/followup-question-aggregation-incremental.txt`.
    *   In `question_aggregator.go`, replace the call to the mock function with a real call to the LLM, passing the new raw questions and the existing normalized questions.
    *   Ensure the code correctly parses the live JSON response from the LLM.

3.  **Register the Handler:**
    *   Create a handler struct in the `followup` package that implements the new `UserJobEventHandler` interface.
    *   In `cmd/web/main.go`, register this new handler with the user job event dispatcher. This connects the event to the aggregation logic.

**Acceptance Criteria:**

*   ✅ When a user's jobs are processed by the subscription system, the `AggregateUserQuestions` function is automatically triggered.
*   ✅ A real call is made to the LLM provider with the correct payload.
*   ✅ An integration test can be run by triggering `RefreshUserJobs` for a test user. We then manually inspect the live Firestore database and **verify** that the normalized questions generated by the LLM are logical and that all database documents (`user_jobs`, `user_followup_questions`) are correctly created, updated, and linked.
*   ✅ **Verify:** The process is idempotent. Triggering the process again for the same user with no new jobs results in no new LLM calls or database writes.

### Phase 3: Email Response Processing

**Goal:** Implement the ability to receive a user's email reply, use an LLM to extract answers, and store them in the database. This completes the "input" side of the feature.

**Implementation Steps:**

1.  **Implement Email Handler (`response_handler.go`):**
    *   Create a handler that implements the `internal.EmailHandler` interface from `inbox_dispatch.go`.
    *   Implement the logic to extract the `[FAQ-{shortID}]` tracking identifier from the email subject or body.
    *   Implement the `isValidResponse` logic to filter out auto-replies.

2.  **Implement Answer Extraction:**
    *   Create the placeholder prompt file `assets/prompts/followup-answer-extraction.txt`.
    *   Implement the LLM call that sends the email body and gets back the structured XML response.
    *   Write the logic to parse the XML, check the `answer_found` flag, and update the `Answer` field on the correct `Question` document in Firestore.
    *   Implement the fallback for `additional_feedback` to email the contents to a support address.

3.  **Register with Inbox Dispatch:**
    *   In `cmd/web/main.go`, register the new followup `EmailHandler` with the main `InboxDispatch` service.

**Acceptance Criteria:**

*   ✅ An integration test can be performed by manually crafting and sending an email (with a valid tracking ID) to the application's inbox.
*   ✅ **Verify:** The `EmailHandler` is triggered.
*   ✅ **Verify:** The correct `Question` document in Firestore is updated with the extracted answer.
*   ✅ **Verify:** The `ResponseReceivedAt` field is set on both the `Question` and `EmailTracking` documents.
*   ✅ **Verify:** If `additional_feedback` is present in the mock LLM response, an email is sent to the designated support address.

---

### Phase 4: Nudge Integration & End-to-End Test

**Goal:** Connect the output of the aggregation to the `internal/nudge` package to send the actual emails to users, completing the full, end-to-end feature loop.

**Implementation Steps:**

1.  **Modify Nudge System:**
    *   This work is likely in the `internal/nudge` package.
    *   Implement the logic for the nudge processor to query the `user_followup_questions` collection for eligible users.
    *   It should select the top 3-5 unsent, high-priority questions.

2.  **Implement Email Generation:**
    *   Implement the logic to create an `EmailTracking` document and its unique short ID.
    *   Render the email template, correctly embedding the question text and their unique identifiers (e.g., `Q1-{firestoreDocID}`).
    *   Update the `SentToUserAt` and `EmailTrackingID` fields on the `Question` documents after the email has been successfully sent.

**Acceptance Criteria:**

*   ✅ **Full End-to-End Test:**
    1.  Start with a test user who has unprocessed jobs.
    2.  Run the `subscription_processor` for them.
    3.  **Verify:** Phase 2 triggers and new `Question` documents are created.
    4.  **Verify:** The `nudge` system, on its next cycle, detects these new questions and sends a real email to a test account.
    5.  Reply to that email.
    6.  **Verify:** Phase 3 triggers, the reply is processed, and the `Answer` is stored in Firestore.
*   ✅ All systems work together automatically, from job processing to receiving a user's answer, with no manual steps in between.
