# SF002.2: Structured Conversation

## Overview
The Structured Conversation subfeature enables the system to conduct natural, engaging phone conversations with candidates following a predefined framework. Using Large Language Models (LLMs), the system creates a personalized conversation flow that gathers relevant information about the candidate's skills, experience, and preferences in a natural, human-like manner.

## Status
**Partially Implemented**

## Subfeatures and Their Interactions
This feature is broken down into the following subfeatures for focused implementation
located in the `subfeatures` folder:

1. [SF002.2.1: Conversation Phase Definition System](./SF002.2.1_Conversation_Phase_Definition_System.md)
   - Defines the state machine configuration for conversations
   - Specifies valid phase transitions and requirements
   - Provides phase-specific prompts and configurations
   - Acts as the source of truth for conversation structure

2. [SF002.2.2: Conversation Middleware Framework](./SF002.2.2_Conversation_Middleware_Framework.md)
   - Implements the mechanics of conversation management
   - Monitors conversation state through various middleware
   - Triggers phase transitions based on monitored conditions
   - Executes transitions through the Phase Manager

3. [SF002.2.3: Information Extraction & Processing](./SF002.2.3_Information_Extraction_Processing.md)
   - Extracts structured data during conversations
   - Monitors completion of required information
   - Signals when phase information requirements are met
   - Triggers transitions based on information completeness

4. [SF002.2.4: Error Recovery & Conversation Control](./SF002.2.4_Error_Recovery_Conversation_Control.md)
   - Detects conversation issues and errors
   - Implements recovery strategies
   - Can force phase transitions when needed
   - Highest priority in transition decisions

5. [SF002.2.5: Time & Flow Management](./SF002.2.5_Time_Flow_Management.md)
   - Manages overall conversation timing
   - Enforces phase-specific time limits
   - Triggers transitions based on time constraints
   - Second highest priority in transition decisions

### Component Interaction Model

The subfeatures work together in a coordinated manner to manage conversation flow:

1. **Phase Definition (SF002.2.1) - The "What" and "Where"**
   - Defines valid conversation states and transitions
   - Specifies information requirements for each phase
   - Provides configuration for phase-specific behavior
   - Serves as the central source of truth

2. **Middleware Framework (SF002.2.2) - The "How"**
   - Implements the Phase Manager to execute transitions
   - Provides middleware infrastructure for monitoring
   - Manages transition request priority and execution
   - Coordinates between monitoring components

3. **Monitoring Components (SF002.2.3-5) - The "When"**
   - Monitor specific aspects of conversation
   - Request transitions through Phase Manager
   - Follow defined priority hierarchy:
     1. Error Recovery (SF002.2.4) - Priority 1
     2. Time Management (SF002.2.5) - Priority 2
     3. Information Extraction (SF002.2.3) - Priority 3

## Detailed Requirements

### Conversation Framework
1. Design a structured conversation flow with distinct phases:
   - Introduction and purpose explanation
   - Verification of resume information
   - Experience exploration
   - Skills assessment and expansion
   - Preference gathering (location, work style, compensation, etc.)
   - Next steps and conclusion
2. Ensure the conversation feels natural rather than scripted
3. Adapt questioning depth based on candidate responses
4. Limit total conversation length to 15-20 minutes
5. Ensure all critical data points are collected by the end of the call

Implementation Note: This framework will be implemented using OpenAI's realtime API (https://platform.openai.com/docs/api-reference/realtime) with GPT-4 as the LLM. The `/workspaces/go-openai-realtime` library will be used to interact with the realtime API. The LLM will be prompted to handle the conversation flow according to the defined phases.

### Dynamic Conversation Planning
1. Use a standardized base prompt template that includes:
   - Candidate's resume
   - Phase definitions from SF002.2.1 Conversation Phase Definition System
   - Required information gathering guidelines
2. The Phase Definition System will guide the LLM to ensure all required information is gathered
3. Prepare follow-up questions for ambiguous or incomplete information
4. Create a balance between confirming known data and gathering new insights

### Conversation Management
1. Implement turn-based dialogue system using OpenAI's realtime API:
   - System speaks/asks questions (TTS via realtime API)
   - Candidate responds (voice recognition via realtime API)
   - System processes response
   - System formulates next statement/question
2. Handle conversation flow control through coordinated components:
   - Phase Manager executes topic transitions
   - Middleware monitors conversation state
   - Information Extractor tracks completion
   - Time Manager ensures pacing
3. Manage timing and pace through Time Management middleware:
   - Appropriate pauses between turns
   - Detection of candidate speaking vs. silence
   - Interruption handling
   - Phase and overall time management

Implementation Note: A sample project demonstrating the realtime API integration, including turn-based dialogue, voice recognition, and TTS will be provided. Request this sample when implementation begins.

### Error Recovery & Fallbacks
1. Implement detection and recovery for:
   - Misunderstood responses (handled by OpenAI's realtime API)
   - Non-responsive candidates (handled by custom middleware)
   - Off-topic answers (detected by separate LLM in middleware)
   - Technical difficulties
2. Create fallback strategies for:
   - Questions candidate can't or won't answer
   - Poor audio quality scenarios
   - Unexpected conversation directions
3. Provide graceful transitions when changing topics
4. Include mechanisms to guide conversation back to structured flow

Implementation Note: Off-topic detection will be handled by a separate LLM in middleware that analyzes the conversation. When off-topic content is detected, the middleware will inject a "developer" message into the conversation thread to guide the primary LLM back on topic.

## User Experience
1. Begin with a clear introduction explaining:
   - Who/what is calling
   - Purpose of the call
   - Expected duration
   - Privacy considerations
2. Use a warm, professional tone throughout the conversation
3. Make the interaction feel like talking to a helpful recruiter
4. Provide clear transitions between conversation topics
5. End with clear next steps and expectations
6. Avoid feeling robotic or script-like

### Conversation Plan Generation Example
```go
func generateConversationPlan(ctx context.Context, db *sql.DB, userID int64) (*ConversationPlan, error) {
    // Fetch user data
    user, err := getUserByID(db, userID)
    if err != nil {
        return nil, fmt.Errorf("failed to get user: %w", err)
    }
    
    // Fetch candidate skills
    skills, err := getCandidateSkills(db, user.CandidateID)
    if err != nil {
        return nil, fmt.Errorf("failed to get skills: %w", err)
    }
    
    // Create input for LLM
    input := map[string]interface{}{
        "resume": user.FullResume,
        "name": user.FirstName + " " + user.LastName,
        "existing_skills": skills,
        "missing_data": identifyMissingProfileData(user),
    }
    
    // Generate conversation plan using LLM
    prompt, err := template.New("conversation_plan").Parse(`
        You are an AI assistant conducting a phone interview with {{.name}}. 
        You need to gather information about their skills, experience, and job preferences.
        
        Here is their resume:
        {{.resume}}
        
        Skills already identified:
        {{range .existing_skills}}
        - {{.Name}} (Level: {{.Level}})
        {{end}}
        
        Missing information to collect:
        {{range .missing_data}}
        - {{.}}
        {{end}}
        
        Create a conversation plan with the following sections:
        1. Introduction
        2. Resume verification questions
        3. Skills assessment questions
        4. Experience exploration questions
        5. Preference gathering questions
        6. Conclusion and next steps
    `)
    if err != nil {
        return nil, fmt.Errorf("failed to parse prompt template: %w", err)
    }
    
    var promptBuf bytes.Buffer
    if err := prompt.Execute(&promptBuf, input); err != nil {
        return nil, fmt.Errorf("failed to execute prompt template: %w", err)
    }
    
    // Call LLM API
    response, err := llmClient.GenerateContent(ctx, promptBuf.String())
    if err != nil {
        return nil, fmt.Errorf("failed to generate conversation plan: %w", err)
    }
    
    // Parse LLM response into structured plan
    plan, err := parseConversationPlan(response)
    if err != nil {
        return nil, fmt.Errorf("failed to parse conversation plan: %w", err)
    }
    
    return plan, nil
}
```

### Conversation Turn Example
```go
func handleConversationTurn(ctx context.Context, callSID string, conversationState *ConversationState, candidateInput string) (string, error) {
    // Update conversation history with candidate's input
    conversationState.History = append(conversationState.History, Message{
        Role: "candidate",
        Content: candidateInput,
    })
    
    // Prepare prompt with conversation history and current state
    prompt := buildConversationPrompt(conversationState)
    
    // Call LLM to generate next assistant response
    response, err := llmClient.GenerateContent(ctx, prompt)
    if err != nil {
        return "", fmt.Errorf("failed to generate response: %w", err)
    }
    
    // Extract assistant message from response
    assistantMessage := extractAssistantMessage(response)
    
    // Add to conversation history
    conversationState.History = append(conversationState.History, Message{
        Role: "assistant",
        Content: assistantMessage,
    })
    
    // Extract and store any gathered information
    if err := extractAndStoreInformation(ctx, conversationState.UserID, candidateInput, assistantMessage); err != nil {
        // Log but continue - critical to not interrupt conversation
        log.Printf("Error extracting information: %v", err)
    }
    
    // Check for conversation completion
    if isConversationComplete(conversationState) {
        // Mark as complete and schedule wrap-up
        scheduleConversationWrapUp(callSID, conversationState.UserID)
    }
    
    // Update conversation state in storage
    if err := storeConversationState(callSID, conversationState); err != nil {
        log.Printf("Error storing conversation state: %v", err)
    }
    
    return assistantMessage, nil
}
```

### Middleware Setup Example
```go
func setupConversationMiddleware(conversationID string, db *sql.DB, phaseConfig *PhaseConfig) (minds.ThreadHandler, error) {
    // Create base handler with the LLM provider
    handler := handlers.NewBasic(conversationID, llmProvider)
    
    // Add standard middleware stack
    handler.Use(ConversationLogger())
    handler.Use(PersistMessage(PersistenceConfig{
        DB:             db,
        ConversationID: conversationID,
    }))
    
    // Add phase management middleware
    phaseManager := NewPhaseManager(phaseConfig)
    handler.Use(phaseManager)
    
    // Add time tracking middleware
    timeTracker := NewTimeTracker(db, conversationID, 20*time.Minute, phaseConfig)
    timeTracker.SetPhaseManager(phaseManager)
    handler.Use(timeTracker)
    
    // Add information extraction middleware
    handler.Use(NewInformationExtractor(phaseConfig.GetExtractionConfig(), db, conversationID))
    
    // Add error recovery middleware
    errorRecovery := NewErrorRecovery(db, conversationID, 3)
    errorRecovery.SetPhaseManager(phaseManager)
    handler.Use(errorRecovery)
    
    // Add summarization middleware
    handler.Use(ConversationSummarizer(llmProvider, systemPrompt))
    
    return handler, nil
}
```
