# T004.4.3: Error Handling And Retry

## Task Description
Implement robust error handling and retry logic for LLM match assessments to ensure reliability even when the LLM service experiences transient issues. This includes implementing exponential backoff for retries, handling rate limiting, and providing graceful degradation when the service is unavailable.

## Acceptance Criteria
1. Failed LLM requests are automatically retried with exponential backoff
2. Rate limiting is handled by pausing and resuming processing
3. A maximum retry count prevents infinite retry loops
4. Permanent failures are logged appropriately
5. Jobs can still be displayed to users even if LLM assessment fails
6. The system gracefully handles service outages

1. Create a retry helper in `/internal/utils/retry.go`:
   ```go
   package utils

   import (
       "fmt"
       "log"
       "math"
       "math/rand"
       "time"
   )

   // RetryConfig contains configuration for the retry mechanism
   type RetryConfig struct {
       MaxRetries    int
       InitialBackoff time.Duration
       MaxBackoff    time.Duration
       BackoffFactor float64
       Jitter        float64
   }

   // DefaultRetryConfig returns a default retry configuration
   func DefaultRetryConfig() RetryConfig {
       return RetryConfig{
           MaxRetries:     5,
           InitialBackoff: 1 * time.Second,
           MaxBackoff:     60 * time.Second,
           BackoffFactor:  2.0,
           Jitter:         0.2,
       }
   }

   // RetryWithBackoff retries the given function with exponential backoff
   func RetryWithBackoff(operation func() error, config RetryConfig) error {
       var err error
       
       for attempt := 0; attempt <= config.MaxRetries; attempt++ {
           // First attempt is not a retry
           if attempt > 0 {
               backoff := calculateBackoff(attempt, config)
               log.Printf("Retrying operation after %v (attempt %d/%d)", backoff, attempt, config.MaxRetries)
               time.Sleep(backoff)
           }
           
           // Attempt the operation
           err = operation()
           
           // If successful, return nil
           if err == nil {
               return nil
           }
           
           // Check if error is retryable
           if !isRetryable(err) {
               log.Printf("Non-retryable error: %v", err)
               return err
           }
           
           log.Printf("Attempt %d failed: %v", attempt, err)
       }
       
       return fmt.Errorf("operation failed after %d attempts: %w", config.MaxRetries, err)
   }

   // calculateBackoff computes the backoff duration with jitter
   func calculateBackoff(attempt int, config RetryConfig) time.Duration {
       // Calculate base backoff with exponential increase
       backoff := float64(config.InitialBackoff) * math.Pow(config.BackoffFactor, float64(attempt-1))
       
       // Apply jitter to avoid thundering herd problem
       jitter := (rand.Float64() * 2 - 1) * config.Jitter * backoff
       backoff = backoff + jitter
       
       // Ensure backoff is within limits
       backoffDuration := time.Duration(backoff)
       if backoffDuration > config.MaxBackoff {
           return config.MaxBackoff
       }
       
       return backoffDuration
   }

   // isRetryable determines if an error should be retried
   func isRetryable(err error) bool {
       // Check for specific error types that indicate retry is appropriate
       // For LLM API calls, this typically includes:
       // - Timeouts
       // - Rate limiting
       // - Temporary server errors (500s)
       
       // For now, we'll consider most errors retryable
       // In a production system, this would be more selective
       return true
   }
   ```

3. Add a dead letter queue for failed assessments:
   ```go
   // Constants for NATS subjects
   const (
       MatchAssessmentSubject = "job.match.assessment"
       MatchAssessmentDeadLetterSubject = "job.match.assessment.deadletter"
   )

   // Send to dead letter queue after max retries
   func sendToDeadLetterQueue(app *config.Application, msg MatchAssessmentMessage, err error) error {
       // Annotate the message with error information
       deadLetterMsg := struct {
           Message   MatchAssessmentMessage `json:"message"`
           Error     string                 `json:"error"`
           Timestamp time.Time              `json:"timestamp"`
       }{
           Message:   msg,
           Error:     err.Error(),
           Timestamp: time.Now(),
       }
       
       // Serialize message
       data, err := json.Marshal(deadLetterMsg)
       if err != nil {
           return fmt.Errorf("error marshaling dead letter message: %w", err)
       }
       
       // Publish to dead letter queue
       return app.NatsConn.Publish(MatchAssessmentDeadLetterSubject, data)
   }
   ```

## Technical Notes
- Exponential backoff prevents overwhelming the service during issues
- Jitter helps avoid the "thundering herd" problem when multiple retries occur
- Dead letter queue provides visibility into persistent failures
- Fallback mechanism ensures users still see results even if LLM is unavailable
- Consider implementing circuit breaker pattern for extended outages
