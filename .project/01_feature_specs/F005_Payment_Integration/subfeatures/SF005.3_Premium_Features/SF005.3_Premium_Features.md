# SF005.3: Premium Features Access

## Overview
This subfeature implements access control for premium features available to users who have paid for enhanced services. For the MVP, we will focus on a simple binary tier system (free vs. paid) and leverage the existing tier implementation in the codebase.

## User Stories
- As a candidate, I want to see what premium features are available for purchase
- As a candidate, I want to access premium features after I've paid for them
- As a candidate, I want to understand the benefits of premium features compared to free features
- As a candidate, I want to see how long my premium access will last

## Requirements

### Premium Feature Definition
- Define a clear set of premium features for the MVP:
  1. Increased job search capacity (3 pages for free tier, 50 pages for paid tier)
  2. More frequent automated searches (every 3 days for free tier, daily for paid tier)
  3. Email notifications for new job matches (paid tier only)
- Leverage the existing tier implementation (`free` vs. `mid` tier)
- Use subscription_end_date to determine access rights

### Premium UI Components
- Design clear visual indicators for premium features
- Show upgrade prompts for free-tier users when they encounter premium features
- Display remaining premium access time for paid users
- Create a simple pricing page explaining the benefits of upgrading

### Access Control
- Leverage existing tier-based checks in the codebase
- Implement access control based on subscription_end_date
- Connect payment status to tier access control
- Implement middleware for checking premium access

## Implementation References

### Database Schema
We'll leverage the existing database schema with the candidates table that already has:
- `tier` field (enum: 'free', 'mid', 'top')
- `subscription_end_date` field

```sql
-- Example query to determine if a user has premium access
SELECT 
    id, 
    tier, 
    subscription_end_date > NOW() AS has_active_premium
FROM 
    candidates 
WHERE 
    id = ?;

-- When a one-time payment is processed, we'll update the tier and subscription_end_date:
UPDATE 
    candidates 
SET 
    tier = 'mid', 
    subscription_end_date = NOW() + INTERVAL '30 days' 
WHERE 
    id = ?;
```

### Service Components
```go
// Premium Feature Access
func HasPremiumAccess(candidateID string) (bool, error) {
    var hasAccess bool
    err := db.QueryRow(
        "SELECT subscription_end_date > NOW() FROM candidates WHERE id = $1", 
        candidateID,
    ).Scan(&hasAccess)
    
    return hasAccess, err
}

// Feature Access Middleware
func RequirePremiumAccess(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        candidateID := GetCandidateIDFromContext(r.Context())
        
        hasAccess, err := HasPremiumAccess(candidateID)
        if err != nil {
            http.Error(w, "Error checking access", http.StatusInternalServerError)
            return
        }
        
        if !hasAccess {
            // Redirect to upgrade page
            http.Redirect(w, r, "/upgrade", http.StatusSeeOther)
            return
        }
        
        next.ServeHTTP(w, r)
    })
}
```

## One-Time Payment-to-Premium Flow
1. User makes a one-time payment through Stripe Checkout
2. Webhook receives successful payment notification
3. System updates candidate record:
   - Set tier to 'mid'
   - Set subscription_end_date to 30 days from now
4. User now has access to premium features for 30 days:
   - Can search 50 pages of jobs instead of 3
   - Gets daily automated searches instead of every 3 days
   - Receives email notifications for new job matches
5. After 30 days, premium access expires automatically
